# coursekit roadmap

The forward-looking view.
For the detailed record — measurements, dated decisions, per-course results — see the working log (kept offline).
This file is the map; the log is the diary.

## Vision

> coursekit turns a course's own material into Canvas-ready artifacts that are **correct, well-taught, and reviewable** — locally, and measurably.

Every decision checks against that line: does it make artifacts more correct, better-taught, more reviewable, or the tool more usable to a real instructor?
If not, it goes to the parking lot.

## How we work (the cadence)

1. **One active focus at a time.** A single _current milestone_ (below). Everything else waits.
2. **Parking lot.** A new idea gets written down immediately so it is never lost — and is **not acted on** until a regroup. Ideas are welcome; acting on them mid-focus is not.
3. **Every milestone has a "done when."** A concrete, ideally measurable acceptance (e.g. "recall > X", "5/5 discrimination", "the review runs from one command"). No open-ended work.
4. **Regroup at milestones.** When the current thing lands: review the parking lot, re-prioritise, pick the next focus. Only then.

## Workstreams

Four workstreams. Each: the goal, where it stands, and the next move.

### 1. Generate — artifacts from a course's material

- **Goal:** good quizzes and pages (later: assignments, modules, discussions, rubrics) from any course.
- **Status:** quizzes + pages solid — canonical IR (`bank.json` / `page.json`), hardened tool-call loop, design system, emitters. This is the mature, steady core.
- **Next:** steady; new generators are a breadth decision, not a current need.

### 2. Evaluate — measure quality, and improve from it

_(Evaluation exists to improve; the loop-back is its point — so "improve" lives here.)_

- **Goal:** trustworthy, measurable quality gates that raise generation quality.
- **Status:** **all three checks built + calibrated** —
  - _Facticity_ (is it correct?): quiz + page critics, domain-aware; ~98–100% recall / 0% false-flag on the synthetic sets; validated on a real course.
  - _Form_ (does it scan/signal/engage/retrieve?): the pedagogy rubric; 5/5 discrimination; drove a real prompt loop-back (course pedagogy 9.25 → 13.5 / 15).
  - _Concept delivery_ (does it actually teach the concepts?): v1; 3/3 discrimination with graded middle.
  - Backed by synthetic calibration infra (`synthesize`, `scoring`, the scorecards).
- **Next:** the loop is closed — `evaluate --all` reports all three checks and `fix` repairs flagged items in place. Parked deepenings: the coherence/development-adequacy dimension and the visual (render-and-see) pass.

### 3. Profiles — work across domains and teaching styles

- **Goal:** the tool adapts to different subjects and different instructors, composably.
- **Status:** the `domain.md` profile exists and now feeds both generators _and_ critics. Everything else is a parking-lot idea.
- **Next:** (parked) composable domain bases + a domain-suggester; pluggable pedagogy strategies; a voice/tone profile.

### 4. Deliver & course-scope — into Canvas, and across weeks

- **Goal:** artifacts land in the LMS; the tool can reason about a whole course, not just a week.
- **Status:** file delivery solid (QTI `.zip`, HTML, CC, whole-course `.imscc` — verified in real Canvas). Course-level reasoning and any API/extension path are unbuilt.
- **Next:** (parked) Canvas API/extension; a course-level evaluator (pacing, spacing, sequencing); the front-end / form-factor track.

- **Composable generation — the attention/crowding answer** `[generate/arch]` (user, 2026-07-31) — instruction crowding is a first-order, GROWING concern: the monolithic single-shot page generation overloads a small model's finite attention, and every capability we add (images, concept checklist, contrast, one-idea) taxes the same budget. **Already biting** — the same root cause explains the fading retrieval foldouts, errors clustering later in a long generation, and the `--detail full` runaway. **Direction:** decompose generation into focused sub-tasks, each with a tight instruction set + small context, so crowding can't happen — and the **concept map is the natural decomposition seam** (it is already the plan): one pass for the frame (hook + enduring understanding + recap from prereqs), one focused pass PER concept (its material + KCs + "teach this one thing well"), one for the close (summary + retrieval), then a light assembler. **Two separable axes:** (1) decompose the GENERATION (attacks attention); (2) emit MULTIPLE pages per week — per concept or grouped — which segments pedagogically (CLT), aids navigation, AND is authentic to the real course (the CC101 module is many wiki pages, not one giant page); generating per-page gives both benefits at once. **Validate empirically first (the project's calibration discipline):** an A/B — same week generated monolithically vs concept-map-decomposed — scored by the three existing evaluators (facticity error rate, pedagogy RETRIEVAL, concept-delivery). That measures whether decomposition lifts quality before a big rewrite. **Cost:** a real architecture change (Generator seam runs one conversation per unit today; this needs several sub-conversations + an assembler + a coherence/through-line layer, more model calls but each smaller/faster/higher-quality). This is the scaling answer for staying quality-competitive on LOCAL models as the tool gets richer. **Sharpened 2026-08-04 (session evidence + an assessment plan before the rewrite).** Separate TWO burdens, because they have different fixes: (1) **instruction load** — how many standing rules + how much transcript sit in the prompt (domain, voice, concept checklist, images, contrast, retrieval gate all compete for the same attention); (2) **output scope** — how much the model must emit in one uninterrupted pass (a whole page of N sections, a whole bank of N×4). Reducing (1) = trim/route instructions; reducing (2) = decompose the output; do both. **Fresh evidence it's biting now, not later:** the page heading-order break (all headings dumped at the end, appeared only once voice added load — the model shed a hard structural rule); the quiz form-mismatch (a conceptual "why/benefit" stem paired with code-snippet options) that PERSISTED across regens; the hook-anchoring (latching onto the one in-prompt example = load-shedding); and a **negative A/B** — scoping voice out of quiz stems did NOT lower the flag rate, so voice was not the driver, which itself argues the burden is STRUCTURAL (juggling the position rule + type mix + coverage + distractor plausibility at once) rather than any single instruction. **Modularization levers beyond per-concept passes:** (a) **route** instructions to only the blocks that need them (voice→prose not code, contrast→only a wrong-vs-right, retrieval→once at the close); (b) **move deterministic work out of the model** — the "half must be MC" type mix (assign up front), the correct-index rotation (shuffle options to the target index post-hoc), section assembly (the model already fails it), glossary/key-terms placement — every deterministic thing removed frees attention for the only thing the model is needed for, judgment; (c) **feed sharper material** — a concept's own slice/KCs, not the whole raw transcript. **How to assess what context earns its place (measure, don't guess) — the four probes:** (1) **ABLATION via the run-store** — remove one component, regenerate, measure the flag/pedagogy delta; removal that doesn't hurt = dead weight, removal that helps = active crowding (the voice scoping was an informal ablation, and it came back negative); the archived `evals/` runs are the substrate. (3) **INSTRUCTION-ADHERENCE probes** — how often each hard rule (heading interleave, index rotation, option-type match) is obeyed early vs. late; a rule kept at the top and dropped at the bottom is being crowded out, and names WHICH instruction is fragile. (4) **TOKEN accounting** — the prompt's share that is transcript vs. standing instructions vs. domain vs. voice vs. concept map; shows the shape of the burden. **Plan: measure before rewriting.** Run ablation (#1) + error-position (#2) first (cheap; #2 needs no model and works on runs already generated), harvest the deterministic wins now (type mix / index rotation / assembly — safe and immediate), THEN commit to the per-concept decomposition with numbers in hand rather than a blind rewrite. The coherence/through-line layer is the real cost of decomposition (a per-concept pass loses the global view). - **Representing a non-linear / revisiting lecture in a page** `[generate/arch]` (user, 2026-08-04) — the decomposition + boundary segmenter assume concepts are taught roughly IN ORDER (one contiguous span each); a lecture that SPIRALS — teaches A, then B, then returns to A deeper — breaks that, and the current segmenter misses the later return. - **Correctness vs style — "clunky but working" as pedagogic value, not a flag** `[evaluate]` (user, 2026-08-04) — the facticity critic flagged working-but-clunky code (a `move()` method that also draws — should arguably be `update()` or split) as "incorrect". - **Teaching is temporal — show the settled conclusion, not a transient state** `[generate/analyze/arch]` (user, 2026-08-04) — a decomposed page reproduced VERBATIM a transient buggy code state (`fill(this.fill) // apply the gradient`, which doesn't work) that the lecture CORRECTED later in the same source (`drawingContext.fillStyle = this.fill`). The critic correctly flagged it (true positive — the net worked). Root cause: teaching is iterative (wrong→right, naive→refined) and the transcript captures every state, but a PAGE should present the settled/working conclusion, not an intermediate. The correction IS in the source, so the transcriber did not lose it — the fix is mostly downstream. Layers, cheap→deep: (a) **page-gen PROMPT** — "when an idea evolves (buggy/naive then corrected), teach the FINAL working version; use an earlier wrong version only as an explicit, labelled contrast, never as the working example" — requires segmentation to include the correction in the concept's span (may not have; check). (b) **FIX LOOP** — the critic already flagged it and the correction exists later in the material, so `fix` could regenerate the block with the corrected code (self-heal via the net that caught it). (c) **TRANSCRIBER** — the vision analysis samples every ~10s indiscriminately, faithfully recording transient states but not MARKING which is settled; it could annotate code evolution or "settle" a code block to its final form so everything downstream sees the conclusion (bigger, transcriber-side, the most principled). A genuinely hard temporal→static translation problem, and the productive edge of the "quality vs near-miss" evaluator theme. **Fix-loop test 2026-08-04 — NOT solved, but it sharpened why.** Ran `--fix` on week-8: the fixer reached "not incorrect" but not "the settled conclusion" — for the clunky `move()` it reached BACKWARD to an earlier WORKING version of the class (a different timeline point, not the intended final form); the buggy gradient became code-LESS prose (the no-invention guard omits code rather than show the wrong version or find the right one). Cheap, imperfect (the last mention isn't always the conclusion), a real default. So: the facticity NET + fix loop are solid (that half is done); what's unsolved is CURATION to the best form — recency heuristic, or the transcriber marking settled states, or human vetting (block-edit UI).
