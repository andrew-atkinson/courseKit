Local-first course authoring

coursekit

A course's own material becomes correct, well-taught, Canvas-ready quizzes and pages — on a model you run yourself.

◆ runs on your machine ◆ no cloud, no API token ◆ Python · a command-line tool

The one load-bearing idea

Every input converges on one canonical form — bank.json for quizzes, page.json for pages — and every export reads only that form.

Adding a new LMS or file format is one new emitter, not a rewrite. The model commits each finished piece through a structured tool call rather than free text, so a revision overwrites its slot instead of piling up discarded drafts.

How the work flows

Five phases, in order

A small pipeline; each phase is a verb, and it's always clear which ones call the model and which run fully offline.

01
ingest

Turns a week's documents — PDF, PowerPoint, Word, ODT, text, Markdown — into the consolidated week text the generators read. A folder of readings and slides becomes one source-tagged week document.

offline
02
propose

Scans a course tree and declares its structure — weeks and typed sources — into an explicit manifest, rather than guessing from filenames. It surfaces any file it couldn't place instead of silently dropping it.

offline
03
analyze

Builds each week's concept map — an instructor-editable list of the concepts a week teaches — which grounds both generation and evaluation.

uses model
04
generate

Turns week text into randomized quizzes and designed pages. Target the whole course, selected weeks, or a single document for an à-la-carte quiz. A run ends with a cold-read review of what it produced, by default.

uses model
05
emit

Packages the canonical JSON into LMS files: a Canvas quiz .zip (QTI), page HTML, a Common Cartridge .imscc of pages, or one whole-course .imscc of pages and quizzes in weekly modules.

What it produces

Quizzes & pages

Randomized quizzes

Each concept becomes a group of variant questions, and every student draws a different variant per concept. A hardened tool-calling loop copes with an unreliable local model — guardrails are written as steering, so a rejected question becomes a correction rather than a failed run.

  • multiple choice
  • multiple answer
  • true / false
  • short answer
  • numerical
  • matching

Designed teaching pages

Not text dumps — pages compose from a catalog of typed blocks (headings, pull quotes, columns, cards, glossaries, code, predict-then-reveal foldouts), each chosen for a documented function drawn from Cognitive Load Theory and Universal Design for Learning.

A page takes one of three functions, and the teaching generator auto-selects a monolithic or decomposed strategy by length.

  • teaching
  • glossary
  • overview

Canvas-safe by construction

Everything renders to HTML restricted to the properties Canvas's sanitizer actually allows, so it survives import intact — including flexbox layout and native collapsible sections. Instructor-supplied links and embeds enter through a per-course supplements file; the model is never allowed to invent a URL.

A design system, not a stylesheet

Four shipped visual identities — each a full design language of type, spacing, shape, and color — chosen per course and applied at render time, so a theme change re-renders every page with no model involved.

  • terminal

The part most tools don't have

Evaluation, not just generation

coursekit measures whether the result is pedagogically sound — five calibrated critics that read already-generated content off disk. evaluate --all runs the battery and writes a report per dimension; fix regenerates each flagged item in place and re-renders.

Facticity

quiz · page

Is each claim or answer correct?

The correctness floor — a question or a page statement that's simply wrong gets flagged.

Pedagogy rubric

page

Does it scan, signal, engage, show examples, prompt retrieval?

Scored 0–3 per dimension with coaching notes, not a pass/fail verdict.

Concept delivery

page

Is each concept actually conveyed well?

For every concept the week teaches — is it explained, exemplified, and pitched at the right level?

Groundedness

quiz · page

Is this from the source, or the model's own knowledge?

A low-coverage quiz warns the source is too thin to ground it; on pages, contradictions with the material are flagged.

The audit → repair loop

quiz · page

Because the critics read finished artifacts off disk, you can audit a course you already have — then fix repairs exactly the flagged items, quizzes and pages alike (including glossary and overview pages), and re-renders so a just-flagged item is corrected at once.

Why it's built this way

Local-first, portable, faculty-owned

Your machine, your model

It runs against a model you host — LM Studio by default, or any OpenAI-compatible provider — so course material and intellectual property never leave your machine. No cloud dependency, no per-seat cost.

Pinned to the right domain

A per-course domain profile keeps every generator in the correct knowledge domain — p5.js, not Processing — and corrects a transcript that drifts.

No token required

The output is standard, reviewable import files that work without an LMS API token — which matters for the many adjunct and contingent faculty who can't get one.

A clear content boundary

By design it handles instructor-authored material only, never student submissions — which keeps it clear of FERPA scope.

Where it stands

Status

Today coursekit is a working command-line prototype — a fit for the technically comfortable early adopter. The generation and evaluation engines are real and run offline against a fast test suite.

The road ahead is largely the interface: a friendly app any instructor could use, and eventually a packaged desktop application with the local model bundled in.
